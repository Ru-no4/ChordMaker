# マルチトラックDAW化プロジェクト

現状ChrodMakerは「コードトラック」が1本だけの構成になっている。将来的に
Cubase/Ableton的な「複数トラックを追加し、それぞれ別の音源・音量で同時再生できる」
構成へ進化させるための段階移行プロジェクト。このドキュメントは、承認済みの移行プラン
と、現在どこまで実装が進んでいるかを記録する。

## スコープ

同じ性質（コードブロック方式）のトラックをN本、それぞれ独立した音源・音量で
持てるようにするところまで。以前検討した「リズム/ステップシーケンサー的な
別種のトラック」は本プロジェクトのスコープ外。将来別種のトラックを足す余地は
残すが、今回は設計しない。

## 重要な設計判断

**Undo対象の分離を維持すること。** 従来 `instrumentId`・`volumeDb`・
`chordTrackHeight` は意図的にUndo対象外（`DocSnapshot` に含まれない）だった。
トラック化する際、これらを `blocks` と同じ構造体に雑にまとめると「音源を
変えただけでUndo可能になる」という従来と異なる挙動が紛れ込む。

そこで各トラックを2つに分離した：

- `tracks: Track[]` = `{ id, name, color, blocks }` … **中身**。Undo対象
- `trackSettings: Record<trackId, TrackSettings>` = `{ instrumentId, volumeDb, muted, solo, height }` … **設定**。Undo対象外

この分離が以降すべてのフェーズの土台になる。

### フェーズ2: 音声エンジンのトラック化（最難関）— 完了

`AudioEngine` の単一シンセ/サンプル/Partを `Map<trackId, TrackChannel>` に
一般化した。`setNotes()` → `setTracks(TrackNotes[], loopRange)` に変更。
UIはまだトラック1本のまま（`useTransport.ts` は `store.tracks` 全体を
エンジンへ渡すようにしたので、フェーズ3でトラックが増えても
そのまま追従する）。

**実装内容:**

- `src/lib/audio.ts`
  - `TrackChannel` クラスを新設。`synth`・`sampled`・`part`・`volume`
    （`Tone.Volume`、共有 `reverb` へ接続）・`activeVoices`・音源読込状態
    などをトラックごとに個別に持つ。`ensureStarted()` 前でも
    `setTracks`/`loadTrackInstrument`/`setTrackVolumeDb` を呼べるよう、
    実際の Tone/AudioNode 構築（`buildChannelNodes`）は `built` フラグで
    遅延させている
  - `sampledGainCache`（学習済み補正ゲイン）と `targetRms`
    （基準ラウドネス）はプラン通りエンジン全体で共有し、同じ音源を
    2トラックが使っても再計測しない。一方、計測用のアナライザー
    （`synthAnalyser`/`sampledAnalyser`）はチャンネルごとに分離し、
    他トラックの同時発音が計測に混入しないようにした
  - `setNotes(notes, loopRange)` → `setTracks(TrackNotes[], loopRange)`。
    渡された `trackId` の集合と現在保持しているチャンネルを突き合わせ、
    含まれなくなったトラック（削除された）のチャンネルは自動で `dispose()`
    する
  - `loadInstrument(id)` → `loadTrackInstrument(trackId, id)`、
    `currentInstrumentId` getter → `currentTrackInstrumentId(trackId)`、
    `previewNotes(midis)` → `previewNotes(trackId, midis, duration)`
  - `setVolumeDb(db)` は既存どおりマスターフェーダーとして残し、
    新たに `setTrackVolumeDb(trackId, db)` を追加（ストア側の
    `trackSettings[id].volumeDb` と対応）
  - トラックごとのシンセの `maxPolyphony` はプラン通り64→16の運用値に
- `src/hooks/useTransport.ts`
  - `blocks`（アクティブトラックのみ）を見ていたところを `tracks`
    （全トラック）に変更し、`audioEngine.setTracks()` へ全トラックぶんの
    ノートをまとめて渡すようにした
  - 音源読み込みの effect もトラックごとにループする形に一般化
  - `tracks` 自体はブロック編集のたびに参照が変わるため、無関係な
    effect（音源読み込み・トラック音量反映）まで毎回走らないよう、
    トラックIDの集合だけを安定した依存値として切り出した
    （`trackIdsKey`/`trackIds`）

**検証中に見つけた不具合と対処:**

- 複数チャンネルの `Tone.Part` を頻繁に作り直すテスト（`setTracks` を
  短時間に連続で呼ぶ）で、`Tone.Part.stop()` が浮動小数点誤差
  （`-1.8e-12` のようなごく僅かな負値）により `RangeError` を投げることを
  確認した。直後に `dispose()` して新しい `Part` を作り直すだけの処理
  なので、`stop()` 自体の成否は結果に影響しない。`scheduleChannelPart`
  と `TrackChannel.dispose()` の両方で `try/catch` により無視するよう
  修正済み（コードベースの他箇所にある smplr 由来の同種の対処と
  同じスタイル）

**検証結果（実機ブラウザ・コンソールから直接エンジンAPIを叩いて確認）:**

- 既存の単一トラック挙動は完全に同一：再生/一時停止/停止、音源切り替え
  （内蔵シンセ・サンプル音源とも）、鍵盤プレビュー、音量、ループ、
  すべて回帰なしで動作
- UIはまだ1トラックのみのため、ブラウザコンソールから
  `audioEngine.loadTrackInstrument('trk-test-2', ...)` 等で2本目の
  ダミーチャンネルを追加し、`setTracks()` で本物のトラックと同時に
  スケジュールして再生 → エラーなし
- 2本目のチャンネルを `setTracks()` から除外して削除 →
  `currentTrackInstrumentId()` が既定値に戻り、チャンネルが確実に
  破棄されたことを確認。既存トラックのチャンネルは影響を受けない
- 同じ音源（Acoustic Grand Piano）を2つ目のチャンネルで読み込んだ際の
  読み込み時間が約118msと、初回のフルダウンロードより明らかに短く、
  二重ダウンロードを避けられていることを示唆する結果を確認
  （ブラウザのHTTPキャッシュに依存しており、エンジン側で明示的な
  重複排除キャッシュは実装していない）
- `tsc -b` / `vite build` ともにクリーン

**追記（フェーズ3の動作確認中に発覚・修正）:** 実際に再生すると音がほぼ
聞こえない不具合があった。原因はトラックフェーダーの既定値。音声経路が
`synth/サンプル → トラックフェーダー → reverb → マスターフェーダー →
limiter` の直列接続になったが、トラックフェーダーの既定値がマスター
フェーダーと同じ `DEFAULT_VOLUME_DB`（-30dB）を流用していたため、既定状態で
-30dB が二重に掛かり実質-60dB相当まで下がっていた。トラックフェーダーの
既定値を別定数 `DEFAULT_TRACK_VOLUME_DB = 0`（素通し）に分離し、音量調整は
従来どおりマスターフェーダー1つに任せる形に修正した（`useProjectStore.ts`）。
実機で `Tone.Volume` の実値を確認し、マスター-30dB・トラック0dBで
フェーズ2以前と同じ実効音量に戻ったことを確認済み。

**追記（フェーズ3のUI確認後に指摘・修正）:** レーンの高さの決め方を見直した。
- 縦ズーム（`chordZoomY`）は元々ブロックの太さだけを変え、レーンの高さは
  トラックごとの `trackSettings[id].height`（境界のドラッグで個別に手動調整）
  が別に決めていた。トラック数が増えたときにズームで見やすく調整できる
  意図が失われていたため、レーンの高さも `chordZoomY` から一律に決まる形
  （`laneHeight(chordZoomY)`）に変更し、`TrackSettings.height` は廃止した
- 境界のドラッグ（`ChordTrackResizeHandle`）が調整する対象も、トラック単位の
  高さではなく「コードトラックエリア全体の表示高さ」（新設の
  `chordTrackAreaHeight`、Undo対象外）に変更。エリアの中に全レーンが積み
  重なり、エリアより中身が高ければ縦スクロールする
- エリアの下限は「既定の縦ズームでレーン1本ぶんを表示できる高さ」で固定
  （トラック数に関係なく一定）、上限はその6倍。以前はトラックが2本あれば
  下限が2本ぶんの高さになってしまい、多トラックでエリアを小さく保つ意味が
  薄かった
- 副次的な修正として、横スクロール時に左端の「小節追加」ボタンが sticky な
  ガターの**上**を通ってしまっていた（z-index の逆転）のを、コードブロックと
  同じくガターの**下**に隠れるよう修正

**追記（BARS行の構造を見直し）:** 「何小節目か・再生範囲」を示すBARS行を、
`position: sticky` でトラックエリアに同居させたまま固定表示していたが、
スクロールバーがトラックエリアと共有される点などが指摘され、DOMレベルで
完全に別行へ分離した。
- BARS行は独自の横スクロール機構を持たない（`overflow: hidden` で中身を
  クリップするだけ）。トラックエリア（`.timeline__scroll`）が横スクロール
  するたびに、その `scrollLeft` の値でBARS行の中身へ
  `transform: translateX()` を直接適用して追従させる（`scrollSync.ts` と
  同じく、再描画を避けるため DOM を直接書き換える方式）。縦スクロールは
  そもそも発生しない（1行だけなので）
- 再生ヘッドはBARS行・トラックエリアそれぞれに1本ずつ描画するよう
  `Playhead` に `showFlag` を追加。旗マーカーはBARS行側だけに出す
- 実機で、横スクロール時にBARS行の中身が正しく追従すること、トラック
  エリアだけを縦スクロールしてもBARS行の位置がまったく変わらないこと、
  ルーラーのクリックでのシーク・再生範囲ハンドルのドラッグが変更前と同様に
  動くこと、2つに分かれた再生ヘッドのX座標が常に一致することを確認
- `tsc -b` / `vite build` ともにクリーン

### フェーズ4: 音源・音量UIの配線 + 選択追従の確認 — ✅ 完了

フェーズ1・2で下準備済みの `trackId` 単位の音源/音量を、トラックヘッダーに
実際のUIとして出した。ピアノロール・選択状態はもともと `activeTrackId` に
追従する設計だったが（`selectActiveTrackBlocks`）、実装中に1点サイレントな
ズレを発見・修正した。

- **`InstrumentSelect` を `trackId` プロップ対応にリファクタ**（`activeTrackId`
  への暗黙依存をやめ、呼び出し側が明示的にどのトラックか渡す）。トラック
  ヘッダー（`TrackLane.tsx` のガター）に音源セレクトと音量スライダー
  （`setTrackVolumeDb`）をコンパクト表示で追加。`ControlBar.tsx` の
  グローバル音源選択は削除（トラックごとの音源はヘッダー側に一本化）。
  マスター音量スライダーはそのまま残し、ラベルを「Master」に変更して

**追記（複数トラック同時再生時の音量について指摘・修正）**

「複数トラックで再生すると音量が単純に倍々になる」という指摘を受け、
原因調査の上で対策した。

- **原因**: 各トラックのチャンネルフェーダーは既定0dB（単一トラック時代の
  名残で素通し）のまま合算され、マスターフェーダーはトラック数に関係ない
  固定値だった。`Tone.Limiter(-1)` はピークのクリッピング防止だけが役割で、
  体感音量（ラウドネス）を一定に保つものではない。つまり「同時に鳴っている
  トラック数に応じてマスター側のゲインを自動で下げる仕組み」が丸ごと
  無かった
- **対策**: `reverb` と `master` の間に自動トリム専用のノード
  （`trackCountTrim`）を追加し、`audioEngine.setAudibleTrackCount(n)` で
  等パワー減衰（`-10*log10(n)` dB）をかける。ユーザーが操作するトラック
  フェーダー・マスターフェーダーとは独立な自動補正として重ねているだけ
  なので、既存の音量UIの意味は変わらない
- **「鳴りうるトラック数」の数え方**: ミュートされておらず（ソロによる
  強制ミュートも含む）、かつノートが1つ以上あるトラックだけを数える
  （空のトラックや聞こえないトラックを数えて過剰に下げないため）。
  再生中の瞬間ごとの発音数を追う真のダイナミック処理ではなく、トラック
  構成やミュート状態が変わったときだけ再計算する軽い実装（プチノイズ・
  ポンピングの回避を優先した）
- `tsc -b` / `vite build` ともにクリーン。実機で、再生中にトラックの
  追加・ミュート切り替えを行ってもエラーやクラッシュが起きないことを確認
  （体感音量の変化そのものは自動テストでは確認できないため、実際に耳で
  確認してもらう必要がある）

  名前で復活すること、通常トラックにノートを追加するとタイムラインの
  ミニプレビューとピアノロールの両方でトラック色のノートが表示され
  コード名/区切り線/鍵盤ハイライトが出ないこと、Ctrl+ドラッグ複製・通常
  ドラッグ移動が問題なく動くこと、`addTrack` のUndo/Redoが正しく効くこと、
  保存→リロードでも `kind` が正しく往復することを確認
- `tsc -b` / `vite build` ともにクリーン

### 追記: デフォルトのコードトラックが縦スクロールしてしまう不具合を修正

フェーズ2〜7の実装後、デフォルトの単一コードトラックがどの縦ズームでも
縦スクロールバー付きになってしまう（1トラックぶんの高さすら確保できて
いない）不具合が発覚。原因は2つ複合していた。

- `lib/grid.ts` の `CHORD_TRACK_AREA_HEIGHT_MIN` / `DEFAULT_CHORD_TRACK_AREA_HEIGHT`
  が「レーン1本ぶんの高さ」しか見込んでおらず、同じスクロール領域
  （`.timeline__scroll`）内に常駐する「トラック追加行」（26px）を計算に
  入れていなかった
- `.timeline__scroll` は横方向にもスクロールする（`overflow-x: auto`）ため、
  横スクロールバーが出ると縦の実効表示領域がブラウザ標準スクロールバーの
  太さぶん（環境依存、Chromium 実機計測で約11px）狭くなり、ぎりぎり収まる
  はずの高さでも縦スクロールを誘発していた

対応として `minChordTrackAreaHeight(zoomY)` 関数を新設し、
`レーン高さ + トラック追加行(26px) + スクロールバー余裕(16px)` を
下限として一本化。さらに `setChordZoomY`/`chordZoomYBy` で、縦ズームを
上げたときはこの下限も追従して引き上げる（下げても縮めない — エリアの
高さはユーザーが手動で広げた分を尊重する、既存の「独立した表示の好み」
という設計を踏襲）ようにした。

**ただしこれだけでは直らなかった。** ユーザーからの再指摘で判明した
本当の原因は、`.chord-lane`（トラックごとのレーン要素）が
`overflow-y: auto` だけを指定し `overflow-x` を指定していなかったこと。
CSS の仕様上、片方の軸だけ `auto` にすると、`visible` のままのもう片方の
軸も計算値としては `auto` 扱いになる（無指定のつもりが実質 `auto` に
なる）。その結果、`.timeline__scroll` 側の共有の横スクロールバーとは別に
**トラックの本数ぶん独立した横スクロールバーが毎回生成され**、それぞれが
自分のレーンの縦の実効高さを削っていた。トラックが増えるほど悪化する
上、横スクロールは元々 `.timeline__scroll` に1つあれば足りるものだった。
`.chord-lane` に `overflow-x: hidden` を明示することで、縦方向の
オーバーフロー（トラック別高さを目一杯まで縮めたときにブロックが
はみ出す場合の救済）だけを残し、余計な横スクロールバーの発生を止めた。
これにより、既定ズームは元より、ズームを最大まで上げても単一トラックで
縦スクロールは発生しない（トラックが2本以上に増えたときにエリア全体が
スクロールするのは、複数トラックを想定した元々の仕様通り）。

### 追記: コードブロックのダブルクリック削除が未実装だった不具合を修正

README（デスクトップの近道）には「ダブルクリック・右クリック = ノート /
コードブロックを削除」と明記されていたが、実装は右クリック
（`onContextMenu`）のみで、ピアノロールのノートには存在する
ダブルクリック削除がコードブロック側には無かった。`ChordBlock.tsx` に
`onDoubleClick` を追加し、ピアノロール側の近道（`usePianoRollGesture.ts`
の `DELETE_SHORTCUT_TOOLS`）と同じ基準で「手」「消しゴム」ツール時は
何もしない（手は非破壊の安全モード、消しゴムは既に単発タップで消える
ため）よう揃えた。
